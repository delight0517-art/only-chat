# Only Chat source ownership and live mutation

- `work-share active` is a resumable task checkpoint, not a source-file lease. Never treat it alone as an active edit conflict.
- Before blocking on another Only Chat task, check its current Codex thread status/last turn, exact `agent-coord` file leases, and actual writer processes for the paths being edited. An idle/completed thread with no exact lease or writer does not own the files. A running Only Chat UI/server process serves the source but is not itself a source writer.
- When reporting a lock or ownership measurement, bind every result to its exact resource (repository/worktree, path, session, or workspace), lock kind, owner, and read time. Path edit leases, workspace execution leases, integration/deploy leases, and product-level runtime state are separate measurements; never combine one into a repository-wide or cross-product “locked/unlocked” conclusion. Missing data means unknown, and “no locks found” applies only to the exact scope that was queried. Re-read the relevant scope before describing it as current.
- Before interpreting a mixed lock result, make a small evidence map with one row per lock source and scope. If a status came from another repository or task, explicitly exclude it from the target repository conclusion. For hot reload or modular evolution, distinguish source edit ownership from runtime reload eligibility and visible runtime confirmation; one does not prove another.
- Before stating that a feature, app, or repository is locked, first name the exact target repository/resource and query that same scope. A `leases_clear: false` value belongs only to the repository and read time returned by that integration-guard call; it does not establish a lock in another repository or a product-level feature lock. Never use a lease result from one product to explain a failure in another. If the queried scope does not match the claim, withdraw the claim and re-read the correct scope before continuing.
- In user-facing lock diagnoses, keep each statement traceable to its evidence row: include the resource, lock type, owner/path when present, and timestamp/source. If no matching measurement exists, say the state is unknown. Do not infer that a source edit, schedule unlock, hot reload, or runtime action failed from an unrelated coordination status.
- This path was historically an Antigravity scratch tree, but the current canonical checkout is Git-tracked on its existing `main` branch. Before editing, verify its live HEAD, exact dirty paths, and `agent-coord` lease; use exact-path leases and commit only the owned paths on `main`. Do not create branches or worktrees. Never infer present source custody from the historical directory name or stale task checkpoint.
- Use the existing Metamorphic Hub only through its supported paths: `.css` changes are stylesheet hot-reloaded; `.html`/renderer `.js` changes request a safe renderer reload and must preserve an in-flight turn, draft, attachments, and conversation; server/core/native module changes need their own verified reload/restart path. Do not claim a live update until the running UI reports/visibly reflects it.
- Preserve the existing running app and unrelated files. Make narrow edits and leave active request/session state intact.
